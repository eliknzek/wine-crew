# אפיון טכני – פרויקט יינות (CrewAI)

## סקירה ועקרונות

המערכת היא Flow אחד של CrewAI שמריץ שני crews בשרשרת: Data Analyst ואחריו Data Scientist. השאלה העסקית: לחזות את ניקוד היין (points) לפי מחיר, מקור, זן ובציר, ולאתר יינות שקיבלו ניקוד גבוה ממה שהמחיר שלהם צפוי לתת.

**עיקרון מרכזי:** הסוכנים מחליטים, מפעילים כלים ומתעדים. כל חישוב נעשה בפונקציות Python דטרמיניסטיות (pandas, scikit-learn) עם seed קבוע. ה-LLM לא מחשב מספרים "בראש", וכותב טקסט רק על בסיס מה שהכלים החזירו. כך נשמרת השחזוריות שהבריף דורש.

**מה עלה בבדיקת הנתונים הראשונית** (winemag-data-130k-v2.csv):

| מדד | ערך |
| --- | --- |
| שורות בקובץ הגולמי | 129,971 |
| שורות כפולות לגמרי | 9,983 |
| חסר מחיר | 6.9% |
| שורות אחרי ניקוי בסיסי | כ-111,500 |
| טווח הניקוד (המטרה) | 80 עד 100, ממוצע 88.4 |
| מתאם ניקוד ללוג המחיר | 0.61 |
| בציר שאפשר לחלץ מהשם | 96.4% מהשורות |
| שגיאת מודל שמנחש ממוצע (MAE) | 2.54 נקודות |
| שגיאת מודל ראשוני בלי דליפה (MAE) | 1.73 נקודות |

**דליפת מידע:** העמודות `description` ו-`taster_name` נוצרות רק אחרי שיין נטעם, ולכן הן לא נכנסות למודל. הן נשארות בנתונים הנקיים לצורכי EDA בלבד, והחוזה מסמן אותן במפורש.

## מבנה ה-repo

כל crew יושב בתיקייה משלו, הכלים הדטרמיניסטיים מרוכזים ב-`tools/`, וכל התוצרים נשמרים ב-`artifacts/` ונכנסים ל-Git.

```
wine-crew/
├── config.yaml              # seed, נתיבים, ספים לבדיקות
├── requirements.txt         # גרסאות נעולות
├── README.md
├── data/raw/                # הקובץ הגולמי (לא נכנס ל-Git)
├── scripts/download_data.py # הורדה מ-Kaggle
├── src/wine_crew/
│   ├── main.py              # נקודת הכניסה: מריץ את ה-Flow
│   ├── flow.py              # WineFlow: השלבים והבדיקות
│   ├── crews/
│   │   ├── analyst/         # agents.yaml, tasks.yaml, crew.py
│   │   └── scientist/       # agents.yaml, tasks.yaml, crew.py
│   ├── tools/
│   │   ├── data_tools.py    # טעינה וניקוי
│   │   ├── eda_tools.py     # סטטיסטיקות וגרפים
│   │   ├── contract_tools.py
│   │   └── model_tools.py   # features, אימון, הערכה
│   └── checks.py            # בדיקות ה-Flow וחריגות מבוקרות
├── artifacts/
│   ├── analyst/             # clean_data.csv, eda_report.html, insights.md, dataset_contract.json
│   └── scientist/           # features.csv, model.pkl, evaluation_report.md, model_card.md
├── logs/                    # לוג לכל ריצה
├── app/streamlit_app.py
└── tests/                   # pytest לכלים ולבדיקות
```

הקובץ הגולמי שוקל כ-50MB ומופץ ברישיון CC BY-NC-SA 4.0. לכן עדיף להוריד אותו דרך הסקריפט ולא לשמור אותו ב-repo. התוצרים קטנים מ-100MB ונכנסים ל-Git כרגיל.

## Crew 1 – Data Analyst

Crew 1 מקבל את הקובץ הגולמי ומחזיר ארבעה תוצרים. הוא מורכב מארבעה סוכנים (הבריף דורש לפחות שלושה) שרצים בתהליך sequential.

| סוכן | תפקיד | כלים | תוצר |
| --- | --- | --- | --- |
| Data Cleaner | טוען ומנקה לפי כללים קבועים, מדווח כמה שורות הוסרו ולמה | `load_raw`, `clean_data` | `clean_data.csv` |
| EDA Analyst | מפעיל ניתוח חקרני ומפיק גרפים | `eda_summary`, `make_charts`, `build_html_report` | `eda_report.html` |
| Insights Writer | הופך את המספרים של ה-EDA לתובנות עסקיות לקניין של רשת יין | קריאת פלט ה-EDA (JSON) | `insights.md` |
| Contract Author | מגדיר את החוזה מתוך הנתונים הנקיים ומוודא שהם עומדים בו | `build_contract`, `validate_contract` | `dataset_contract.json` |

**כללי הניקוי** (בתוך `clean_data`, בסדר הזה):

1. הסרת 9,983 השורות הכפולות לגמרי.
2. הסרת שורות בלי `price`, `country` או `variety`.
3. הסרת העמודות `region_2` (61% חסר) ו-`taster_twitter_handle` (כפולה לשם הטועם).
4. חילוץ `vintage` מתוך `title` (שנה בין 1980 ל-2017; אחרת ערך חסר).
5. הוספת `log_price` = ln(price).
6. ניקוי רווחים ממחרוזות טקסט.

תוצאה צפויה: כ-111,500 שורות, קובץ של כ-45MB.

**גרפים ל-EDA:** התפלגות הניקוד; התפלגות המחיר בסקלת לוג; ניקוד מול לוג מחיר; ניקוד ומחיר חציוניים לפי מדינה ולפי זן (15 הגדולים); ניקוד לפי בציר; מפת ערכים חסרים.

**שאלות ש-insights.md עונה עליהן:** באיזה טווח מחיר הניקוד מפסיק לעלות; אילו מדינות וזנים נותנים ניקוד גבוה במחיר נמוך; איפה הנתונים מוטים (45% מארה"ב אחרי ניקוי).

## dataset_contract.json – טיוטה

החוזה הוא הממשק בין שני ה-crews. הוא קובע אילו עמודות קיימות, מה הטיפוס והטווח של כל אחת, ואילו עמודות אסור להכניס למודל. הטווחים נקבעו לפי מה שנמצא בקובץ האמיתי, עם מרווח קטן למספר הקטגוריות.

השדה `role` קובע מה מותר לעשות עם כל עמודה: `target` (משתנה המטרה), `feature`, `feature_optional`, `identifier` (לתצוגה בלבד), `excluded` ו-`leakage`. Crew 2 נכשל במכוון אם feature כלשהו מגיע מעמודה שתפקידה ברשימה `forbidden_feature_roles`.

הקובץ המלא נמצא ב-`docs/dataset_contract.json`.

במערכת הסופית, `build_contract` יפיק את הקובץ הזה מתוך תבנית קבועה ומתוך הנתונים. ה-LLM לא ממציא את הטווחים. הוא רק כותב את ההנחות במילים.

## Crew 2 – Data Scientist

Crew 2 מקבל את `clean_data.csv` ואת החוזה, מאמן שתי גרסאות מודל ומשווה ביניהן מול baseline. הוא מורכב מארבעה סוכנים.

| סוכן | תפקיד | כלים | תוצר |
| --- | --- | --- | --- |
| Contract Validator | מוודא שהנתונים תואמים לחוזה לפני שנוגעים בהם | `validate_contract` | דוח בדיקה בלוג |
| Feature Engineer | בונה features רק מעמודות שהחוזה מתיר | `build_features` | `features.csv` |
| Model Trainer | מאמן ומעריך את שתי הגרסאות, בוחר את הטובה מביניהן ומדרג יינות שווים למחירם | `train_models`, `evaluate`, `rank_value_wines` | `model.pkl`, `evaluation_report.md` |
| Model Card Writer | כותב מטרה, נתונים, מדדים, מגבלות והיבטים אתיים | קריאת המדדים (JSON) | `model_card.md` |

**Features:**

- `log_price`.
- `vintage`, ודגל שמסמן את השורות שבהן הערך חסר (`vintage_missing`).
- `country`, `province` ו-`variety`. קטגוריה עם פחות מ-50 שורות הופכת ל-`Other` (הסף מוגדר ב-`config.yaml`).
- `region_1` נכנס רק לגרסה 2, כדי לבדוק אם הוא מוסיף משהו.

**המודלים:**

| גרסה | מודל | מה היא בודקת |
| --- | --- | --- |
| Baseline | ניחוש הממוצע | נקודת הייחוס שכל מודל צריך לעבור |
| v1 | Ridge על one-hot | מודל ליניארי פשוט שקל להסביר |
| v2 | HistGradientBoosting | קשרים לא ליניאריים, והוספת `region_1` |

**הערכה:**

- חלוקה קבועה של 80/20 עם `random_state=42`, ובנוסף 5-fold CV על קבוצת האימון.
- מדדים: MAE (המדד הראשי), RMSE ו-R².
- הגרסה שנבחרת נשמרת כ-`model.pkl`.

**דירוג יינות שווים למחירם:** הציון של כל יין מחושב כניקוד בפועל פחות הניקוד שהמודל חזה. התחזית לכל יין מגיעה ממודל שלא ראה אותו באימון (out-of-fold, עם `cross_val_predict`). אחרת המודל "זוכר" את היינות והציון מתכווץ לאפס. הרשימה נכנסת ל-`evaluation_report.md` ומוצגת באפליקציה.

**ב-model card חובה לציין:** הנתונים מ-2017 וממקור אחד; 45% מהיינות מארה"ב (אחרי ניקוי); רק יינות שקיבלו 80 ומעלה נכללו; ניקוד של טועמים הוא סובייקטיבי; הוחרגו עמודות של דליפת מידע; המודל נועד לתמיכה בהחלטה ולא להחלפת טעימה.

## ה-Flow ונקודות הבדיקה

`WineFlow` (מבוסס על `crewai.flow`) מריץ את שני ה-crews ברצף. אחרי כל שלב רצה בדיקה ב-Python שלא תלויה ב-LLM. בדיקה שנכשלת מעלה `FlowCheckError`, וה-Flow תופס אותה ועוצר בצורה מסודרת.

רצף השלבים:

```
Raw CSV + sha256
  → Crew 1 (clean_data, EDA, insights, contract)
  → שער 1: הנתונים תואמים לחוזה?        ── לא → עצירה מבוקרת
  → Crew 2 (validate + features)
  → שער 2: features שלמים, בלי דליפה?    ── לא → עצירה מבוקרת
  → אימון v1 + v2 מול baseline
  → שער 3: המודל עוקף את ה-baseline?     ── לא → עצירה מבוקרת
  → שמירת תוצרים + run_summary.json + לוג

עצירה מבוקרת = הודעת שגיאה ברורה, הבדיקה שנכשלה נרשמת בלוג,
run_summary.json מסומן failed, exit code 1, בלי קריסה.
```

אף שלב לא מתחיל על נתונים שלא עברו את השער שלפניו. בנוסף, לפני הכול נבדק שהקובץ הגולמי קיים, וה-sha256 שלו נרשם.

| שער | מתי | מה נבדק | דוגמה להודעת כשל |
| --- | --- | --- | --- |
| 1 – חוזה | אחרי Crew 1 | כל העמודות קיימות עם הטיפוס הנכון; מספר השורות בטווח; אין כפולות; אין ערכים חסרים בעמודות החובה; הערכים בטווח המותר | `Contract check failed: price has 812 nulls (allowed 0)` |
| 2 – features | אחרי בניית ה-features | כל ה-features הנדרשים קיימים; אין feature מעמודה אסורה; אין NaN; מספר השורות תואם ל-clean_data | `Feature check failed: taster_name is a leakage column` |
| 3 – מודל | אחרי האימון | המודל הנבחר משיג MAE נמוך מה-baseline; `model.pkl` נטען מחדש וחוזה על 5 שורות לדוגמה | `Model check failed: MAE 2.61 >= baseline 2.54` |

## שחזוריות ולוגים

שתי ריצות על אותו קובץ גולמי צריכות להפיק את אותם מספרים בדיוק: שורות, מדדים ודירוג. רק ניסוח הטקסט שה-LLM כותב יכול להשתנות.

- **seed אחד** (`seed: 42` ב-`config.yaml`) לכל פונקציה שיש בה אקראיות: חלוקה, CV ומודלים.
- **טמפרטורה 0** לכל הסוכנים.
- **טביעת אצבע של הקובץ:** ה-sha256 של הקובץ הגולמי נרשם בחוזה ובלוג, כך שרואים על איזה קובץ רצו.
- **גרסאות נעולות** ב-`requirements.txt`, כולל `crewai`.
- **לוג לכל ריצה**, `logs/run_<timestamp>.log`: מזהה ריצה, כל שלב עם זמן התחלה וסיום, מספר שורות בכניסה וביציאה, ותוצאה של כל בדיקה.
- **סיכום מרוכז**, `artifacts/run_summary.json`, שהאפליקציה קוראת.
- **הרצה בפקודה אחת:** `python -m wine_crew.main`.
- **בדיקת שחזור:** ב-`tests/` יש בדיקה שמריצה פעמיים את `clean_data` ואת `train_models` על מדגם קטן ומשווה את התוצאות.

## ממשק Streamlit

האפליקציה רק מציגה את התוצרים שנמצאים ב-`artifacts/` וקוראת ל-`model.pkl`. היא לא מריצה את ה-Flow, ולכן היא עובדת גם בלי מפתח API. זה חשוב לפריסה ב-Streamlit Cloud.

| מסך | מה מוצג | מקור |
| --- | --- | --- |
| סקירה | סטטוס הריצה האחרונה, תוצאות הבדיקות, מספר שורות | `run_summary.json` |
| ניתוח | הגרפים של ה-EDA והתובנות | `eda_report.html`, `insights.md` |
| מודל | השוואת baseline, v1 ו-v2 לפי MAE, RMSE ו-R² | `evaluation_report.md`, `model_card.md` |
| מציאת שווים למחיר | טבלת יינות לפי ציון, עם סינון לפי מדינה, זן וטווח מחיר | קובץ הדירוג |
| חיזוי | טופס של מחיר, מדינה, מחוז, זן ובציר, שמחזיר ניקוד צפוי | `model.pkl` |

עיצוב מתקדם מגיע רק אחרי שה-Flow עובד מקצה לקצה.

## סדר עבודה

המטרה הראשונה היא Flow שרץ מקצה לקצה בגרסה פשוטה. רק אחרי שהוא עובד משפרים כל שלב.

1. **הקמת ה-repo:** מבנה תיקיות, `config.yaml`, `requirements.txt`, תבנית PR וסקריפט הורדה.
2. **כלים בלי סוכנים:** `clean_data`, `build_contract`, `validate_contract`, `build_features` ו-`train_models` כפונקציות Python רגילות, עם בדיקות pytest.
3. **Crew 1** עטוף סביב הכלים, כולל EDA ו-insights.
4. **Crew 2** עטוף סביב הכלים, כולל model card.
5. **ה-Flow** עם השערים, הלוגים ו-`run_summary.json`. מכאן המערכת רצה מקצה לקצה.
6. **שיפור המודל** ודירוג היינות השווים למחירם.
7. **אפליקציית Streamlit** ופריסה (רשות).
8. **README, מצגת של 10–12 שקפים וסרטון דמו של עד 5 דקות.**

אם רוצים להוסיף תאריכים, צריך לדעת מה מועד ההגשה.
